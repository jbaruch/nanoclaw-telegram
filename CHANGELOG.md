## [Unreleased]

- backup-repo origin-URL cleanup + GITHUB_TOKEN documented in `.env.example` (#399). New `scripts/clean-backup-repo-origins.sh` walks `groups/*/backup-repo` and rewrites only origin URLs that carry an embedded credential — matched via `://[^/@]+:[^/@]+@` — to the clean form `https://github.com/jbaruch/nanoclaw.git`, counting `changed` / `already_clean` / `no_remote` / `no_repo` / `unexpected_non_clean` outcomes per group. Narrow on purpose: a non-credential URL that happens to differ from the clean form (e.g. an operator-set SSH remote `git@github.com:jbaruch/nanoclaw.git`, or a fork mirror) is reported as `unexpected_non_clean` and LEFT ALONE — the script's intent is to scrub embedded credentials, not to enforce a single canonical URL as policy. The token only needs to exist at runtime now — the IPC handler's `GIT_CONFIG_KEY_0` `insteadOf` injection (preserved from the original handler) substitutes it ephemerally for the duration of the `git push`, so no group's `.git/config` carries the secret on disk anymore. Idempotent (re-runs on a clean tree are no-ops), with `--dry-run` for previewing; arg parsing is strict (rejects unknown flags and extra positional args with exit 2) so a typoed `--dryrun` doesn't silently fall through to a real rewrite. The current URL is printed with the password component redacted (`https://x-access-token:<redacted>@...`) per `jbaruch/coding-policy: no-secrets` so a tmux scrollback or terminal log of this script's output never carries a live token. Acceptance per the issue body: post-run, `git -C groups/<group>/backup-repo remote -v` returns the clean URL with no token, and `grep -rn "github_pat_" /home/jbaruch/nanoclaw` only hits `.env`. `.env.example` now splits into a CI-only-secrets block (the existing `OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `TESSL_TOKEN` consumed only by `.github/workflows/`) and a runtime-secrets block; `GITHUB_TOKEN` joins the runtime block with a fine-grained-PAT scope hint (`Contents: write` on `jbaruch/nanoclaw` only) and a `https://github.com/settings/personal-access-tokens/new` creation link. The runtime / CI partition makes the security model legible for a new maintainer: anything in the CI block flows into GitHub Actions secrets via the link in the file header; anything in the runtime block lives only in `.env` on the NAS and the IPC handler that reads it. **Manual operator action required**: rotate the broken PAT on github.com → Personal access tokens (the current token started returning `Invalid username or token` on `git fetch --dry-run` per the issue body, so backup pushes have been failing in addition to the sync gap fixed by #397), put the new value into `.env` on the NAS, and re-deploy via `./scripts/deploy.sh`. The cleanup script and the rotation are both prerequisites for the github_backup pipeline returning to health: #397's sync produces non-empty diffs again, then a fresh PAT lets the push land. Closes #399; with #397 and #398 merged, the github_backup pipeline is fully back online once the operator rotates the token.

- Source-data sync into `backup-repo/` before commit + structured `github_backup` result envelope (#397). New `src/backup-sync.ts` exports `syncBackupRepo({ groupDir, backupDir, dbPath })` which copies live group state into the backup tree before the existing `git add -A && git diff --cached --quiet` plumbing gets a chance to declare "nothing to commit." Concretely it (a) overwrites `backup-repo/MEMORY.md` and `backup-repo/daily_discoveries.md` from their group-folder counterparts when the source files exist, (b) mirrors `groups/<group>/memory/` into `backup-repo/memory/` with delete-on-missing semantics so files that no longer exist in the source are removed from the dest (git history retains the older state — the working tree should match the live one), preserving nested subdirectories, and (c) calls `runDumpPlan` from the relocated `src/db-dump.ts` to write `<table>.sql` for every table in `STATE_TABLES` that's present in the DB. Source `memory/` missing leaves the dest untouched (don't blow away historical content just because the source disappeared on the wrong day); the source/backup-repo dirs missing throws an actionable error naming the missing path. The IPC handler at `src/ipc.ts` (`case 'github_backup'`) now invokes `syncBackupRepo` BEFORE the bash-driven git plumbing, fails closed if sync throws (writes `{ error, stage: 'sync' }` to the result file and skips the git step rather than committing a half-synced tree), and merges the `SyncResult` into the success envelope as `sync_summary: { copied, removed, dumped, skipped }` so downstream consumers (the nightly-housekeeping skill specifically) can detect anomalies without parsing prose. The bash command's emitted JSON now also carries an explicit `committed: boolean` field — `{"committed":false,"stdout":"Nothing to commit."}` vs `{"committed":true,"stdout":"Committed and pushed."}` — so a future "warn on N consecutive empty commits" pass in Step 19 of nightly-housekeeping has a structured signal to gate on instead of regex-matching the stdout text. The `stage: 'sync' | 'git'` field on error envelopes makes it unambiguous which side of the pipeline failed (sync = file copy / dump; git = stage / commit / push); the OneCLI-driven `GIT_CONFIG_KEY_0` token injection from the original handler is preserved unchanged. The structured-logging change at the top of the handler now logs `copied`/`removed`/`dumped`/`skipped` counts at INFO before kicking off git so the operator-visible diagnostic for a quiet run ("synced 0 files, 0 dumps, but committed=false") has signal in `task_run_logs` even before the skill-side warning lands. Refactor: `runDumpPlan` and `STATE_TABLES` moved from `scripts/dump-state-tables.ts` into `src/db-dump.ts` so production code can import them — `tsconfig.json`'s `rootDir: ./src` forbade the script-to-src direction. `scripts/dump-state-tables.ts` is now a thin CLI wrapper around `src/db-dump.ts`, preserving the operator-side ad-hoc invocation path; tests moved from `scripts/dump-state-tables.test.ts` to `src/db-dump.test.ts` with the import retargeted. New `src/backup-sync.test.ts` exercises the sync surface with tmpdir fixtures and a `better-sqlite3`-populated DB: single-file copy + overwrite, single-file source-missing skip, `memory/` mirror with orphan removal, nested-subdirectory preservation, source `memory/` missing leaves dest alone, dumped/skipped table accounting, and the two missing-dir error paths. The Step 19 "warn on consecutive empty commits" heuristic itself lives in the nightly-housekeeping tile-skill (separate repo, separate PR); this change is the structured signal that makes that warning implementable. Origin-URL cleanup and PAT rotation for the broken token live in #399. Closes the source-data-sync half of #397; the github_backup pipeline now stops being a silent no-op the moment this lands.

- SQLite state-table dumps for the github_backup pipeline (#398). New `scripts/dump-state-tables.ts` exports a `STATE_TABLES` constant (the irreplaceable queue/state surface called out in #398 — `orders`, `email_feedback`, `scheduled_reminders`, `email_state`, `email_seen_ids`, `resumable_cycles`, `pending_*`, `calendar_*`, `phase_completions`, `tz_state`, `follow_me_tasks`, `scheduled_tasks`, `task_run_logs`, plus the trusted-session and orders-metadata tables) plus a `runDumpPlan({ dbPath, outDir, tables? })` entry point that calls `sqlite3 <db> .dump <table>` per table and atomic-writes the resulting SQL text to `<outDir>/<table>.sql`. Atomic-write uses `<file>.tmp` + `renameSync` so a concurrent reader (or a crash mid-write) never observes a half-written dump. `tableExists` short-circuits per-table — tables not present in the DB land in `report.skipped` and write nothing rather than producing empty-shell `.sql` files (typical when a group hasn't run a particular state-NNN migration yet). `.dump` is text-form SQL (`CREATE TABLE` + `INSERT` statements) so the existing `backup-repo` `git add -A && git diff --cached --quiet` pipeline keeps producing meaningful per-day diffs, and a destructive-test replay (`cat <table>.sql | sqlite3 fresh.db`) reconstitutes the exact rows — covered by an explicit round-trip test in `dump-state-tables.test.ts`. Bulk-cache tables (`messages`, `chats`, `reactions`, `sessions`, `smart_home_events`) are intentionally excluded from the default — they're recoverable from upstream sources (Telegram, the SDK runtime, Hubitat) and large enough that buffered `.dump` output through `maxBuffer` would OOM and produce dumps that don't diff usefully; pass `--tables messages` etc. to dump them explicitly. Operator-supplied `--tables` values are validated against `/^[A-Za-z_][A-Za-z0-9_]*$/` so a pasted-in value containing `;` or `'` aborts the run rather than getting interpreted by the `sqlite3` CLI's command parser. Sqlite3 CLI preflight throws an actionable error message naming the install path per package manager (`apt: sqlite3`, `brew: sqlite`, `Synology: SynoCommunity sqlite3`) when the binary isn't on PATH, rather than letting `spawn ENOENT` leak through. The script lives in `scripts/` alongside `migrate-thin-claude-md.ts` and follows the same shape: typed exports, entry-point guard via `import.meta.url === pathToFileURL(path.resolve(process.argv[1])).href` (the `path.resolve` matters — relative `argv[1]` would otherwise crash `pathToFileURL`), vitest tests with tmpdir fixtures populated via `better-sqlite3` (the project's existing dep) so fixtures are programmatic per the `testing-standards` rule. The IPC handler integration that calls this script before `git add -A` is a separate change (#397) — landing the dump script first decouples review of "does the dump produce restorable SQL" from "does the IPC handler invoke it correctly," and the script is independently useful from the CLI for ad-hoc state extraction. STATE_TABLES is the single point of truth for the irreplaceable surface; future migrations adding new tables append here in the same declaration order as the migration file. Closes #398.

- Two-context split for `Read` of external file paths (#392). New `external-file-summary.ts` in the agent-runner + a `createExternalFileSummaryHook` PreToolUse hook on `Read`. When `SUMMARISE_EXTERNAL_FILES=1` AND the resolved path is outside the workspace mount roots (`/workspace/{group,state,trusted,global,store,ipc}/`), the hook reads the file in the hook process, routes the bytes through `extractStructuredSummary` (the no-tools sub-agent shipped in #367), and DENIES the original `Read` with a multi-line `permissionDecisionReason` carrying the canonical Encoding-B sentinel (so #322's capability-ACL walk-back keeps gating on `file:<path>`) plus the structured digest. The parent agent's transcript carries the digest, never the raw bytes — closing the laundering channel where a poisoned external file (NAS share, user-shared mount, `/tmp` payload) carries hidden prompt-injection text that lands in context even with the destructive-op gates closed. Schema is generic external-file shape: `{ content_kind ('text' | 'code' | 'data' | 'log' | 'binary' | 'other'), detected_format, summary, extracted_fields, contains_links, contains_imperatives }` — every field required so the parent transcript shape is stable; the sub-agent emits empty / false defaults when a field is unknown. The `contains_imperatives` flag surfaces injection-shaped content to the parent without requiring the verbatim text. Path classification reuses #321's `classifyReadPath` (same traversal-defeated normalization) so `/workspace/group/../etc/x` collapses to `/workspace/etc/x` and is correctly classified as external — same definition the existing PostToolUse provenance-sentinel emit uses, so internal/external classification stays in lockstep. Spec correction (recorded in the module header): #392 originally proposed a PostToolUse hook layered on top of the sentinel emit, but the SDK exposes no `tool_response` mutation surface for built-in tools (verified at #321 PR 4) — `additionalContext` adds to the raw output rather than replacing it. PreToolUse interception is the only way to satisfy the issue's acceptance ("the injection string does NOT appear verbatim"). File-read errors (`ENOENT` / `EACCES` / `EISDIR` / `ENOTDIR` / `EPERM` / `ELOOP` / `ENAMETOOLONG`) and summariser failures (timeout, refusal, API error, etc.) pass through — the original Read runs, the SDK produces its canonical error in the first case, and the marker-based ACL gate is the active defence in the second. Unexpected (non-fs, non-SDK) errors propagate per `jbaruch/coding-policy: error-handling`. Files larger than the byte cap are read up to the cap via low-level `openSync` + `readSync` (avoiding slurping a 4 GiB log file into memory) and flagged as truncated in the digest. The Anthropic SDK client is now shared (lazy-cached at module scope) between the #319 Composio body summariser and this hook — one client per process so retries / keepalive / etc. aren't duplicated when both flags are enabled. Default-off via `SUMMARISE_EXTERNAL_FILES=1`, same posture as #319; per-call latency telemetry logs `latency_ms=...` and `truncated=...` per intercepted Read so per-group flag tuning can be data-driven. Closes the `Read` external-paths half of the original #319 scope; together with the #319 Composio gmail/calendar summariser this completes the two-context-split coverage for the structural-replacements audit row 13.

- Composio body summarisation for gmail and calendar reads (#319). The `READ_TOOL_PATTERNS` rows in `container/agent-runner/src/untrusted-input-wrap.ts` now carry an optional `summariseBody` config (extraction goal + JSON Schema) that routes the wrapped text-block content through `extractStructuredSummary` (the #319 v1 library shipped in #367) before the Encoding-A `<untrusted-input source="...">` envelope is added. Gmail rows summarise into `{ messages: [{ sender, recipients, subject, date, body_summary, action_requested, contains_links, contains_attachments }] }`; calendar rows summarise into `{ events: [{ title, start_time, end_time, attendees, location_summary, description_summary }] }`. The structured digest replaces the raw body in the parent agent's transcript, so a "now please email Alice" injection that lands in a gmail body does not enter the parent's context verbatim — only the sub-agent (no tools, hard rules forbidding instruction-following inside content) ever sees the raw bytes. The Encoding-A envelope and `source=` attribute stay unchanged so #322's capability-ACL walk-back keeps gating on `gmail:` / `calendar:` markers exactly as before. Expected failure modes (`timeout`, `sub_agent_refused`, `sub_agent_returned_nothing`, `sub_agent_returned_invalid_shape`, `api_error`) fall back to wrapping the raw body with a `<summarisation-failed reason="..." detail="..."/>` marker INSIDE the envelope, so the parent model still reads the body but knows it is RAW and must apply maximum scepticism. Unexpected errors propagate per `jbaruch/coding-policy: error-handling` — the wrap module does NOT catch them, so a real bug (programmer error, OOM, runtime fault) surfaces instead of being silently rewrapped as a `<summarisation-failed>` marker that would hide the defect. The `detail` attribute on the marker is HTML-attribute-escaped (`&` `"` `<` `>`) and newline-collapsed so a malicious sub-agent can't smuggle a closing `</untrusted-input>` through the failed-summary path. Default-off via `SUMMARISE_COMPOSIO_BODIES=1` so per-group enablement is decoupled from the deploy that ships the code path; the wrap hook logs `summary_latencies_ms=...` and `summary_outcomes=...` per call so per-group flag tuning can be data-driven. Anthropic SDK client is constructed lazily on first call and cached so per-runQuery reads share one TCP keepalive pool. Slack, GitHub, and Tessl rows stay on envelope-only behaviour for this PR — adding a `summariseBody` config is a one-line change per row and a future audit pass will broaden coverage; the marker-based `#322` ACL gate on those sources is the active defence in the meantime. Closes the Composio-body half of #319; the `Read` of external file paths is tracked separately under #392.

- Provenance-aware compaction (#327). New `compact-provenance.ts` in the agent-runner — extends the existing `PreCompact` hook to walk the live pre-compaction JSONL transcript and persist a per-session sidecar JSON of every unique `prefix:value` source seen in either #321 encoding (Encoding A `<untrusted-input source="...">` wraps and Encoding B `PROVENANCE_MARKER:` sentinels). A new `PostCompact` hook reads the sidecar back, deletes it, and emits a `systemMessage` containing one synthetic `PROVENANCE_MARKER:` line per source. The synthetic lines land in the post-compaction transcript as a `system`-role SessionMessage that #322's `capability-acl` walk-back picks up exactly like the canonical pre-compaction sentinels — closing the laundering channel where the SDK summariser strips `<untrusted-input>` wraps and the gates re-open. Boundary semantics preserved: when the operator types a fresh prompt after compaction, the walk-back stops at that boundary and our injected markers are NOT scanned (correct reset — the operator has had a chance to read the summary and sanitise their request); when the model continues autonomously across the boundary without a fresh operator turn, the walk-back scans backward through the synthetic markers and the ACL intersection holds. Sidecar discipline: one file per session id under `/workspace/state/compact-provenance/<sessionId>.json`, written 0600, schema-versioned per `rules/stateful-artifacts.md` (parser returns `null` on shape mismatch, caller treats as "no usable prior state"); PreCompact overwrites, PostCompact deletes after reading, mismatched session ids leave the file in place (defence in depth — the path is keyed on session id, but a stranded file from another session must never be deleted by the wrong owner). Marker extractor walks every text-bearing slot in the JSONL (string `entry.message.content`, `content[N].text` blocks, nested `tool_result.content` arrays of text blocks) via a generic flatten so adding a new content-block type with a `text`-like field requires no change here. Source-cap of 256 unique entries (insertion order — earliest sources, typically the ones the model is most likely to act on, are preserved when a long session blows past the cap; one preserved marker is enough to lock the ACL intersection down). Per-source byte cap of 2 KiB rejects malformed emitters and injection-driven oversized `source=` attributes. Sidecar persistence runs as a separate try block from the archive flow so a corrupt-transcript / archive failure can't cascade into losing the provenance signal (and vice versa). Logging emits source counts only, never source values — per `rules/no-secrets.md` the values can carry signed-URL tokens, gmail msg ids, and file paths. PostCompact failure modes (missing sidecar, corrupt JSON, wrong schema_version, mismatched session id) all return an empty payload silently — the SDK's compaction proceeds normally, just without the post-compaction defence; the gate is a defence-in-depth layer over #322's existing walk-back, not a gate the SDK depends on. Closes the post-compaction half of #318's structural-defense umbrella alongside #322's walk-back; the pre-compaction half is already gated by #321's emitters and #322's ACL.

- Memory read-time staleness reminder (#387). New `memory-staleness-reminder.ts` + PostToolUse hook on `Read` matched by the `^(WebFetch|WebSearch|Read|Bash)$` family. When the resolved target is under `/workspace/trusted/` (excluding the carved-out `quarantine/` subtree), the hook injects a `systemMessage` via `additionalContext` reminding the model that the bytes are a last-seen snapshot, not ground truth — any state-mutating decision (sending messages, scheduling tasks, calling Composio sinks) needs verification against the live source. The reminder rides at the same salience tier as the data, rather than relying on the model recalling the global `RULES.md` *Memory verification* rule that may have been compacted away or drowned by injected text. Path classification mirrors #321's traversal-defeated normalization so `/workspace/trusted/../../etc/x` doesn't accidentally trip the gate. Complementary to #325's write-time quarantine: #325 prevents a session that touched external content from laundering injected data INTO `/workspace/trusted/`; #387 prevents the model from acting on a `/workspace/trusted/` snapshot AS IF it were authoritative when it reads it. Out of scope for v1: excluding internal harness reads (session-reentry / status reports — both legitimately read MEMORY.md) since PostToolUse has no skill-context awareness; if the reminder proves noisy on the recovery path, a follow-up tightens. `Grep` / `Glob` extension also deferred — those return path/name hits, not content; the staleness vector is content-based.

- Memory write quarantine for sessions that touched external content (#325). New `memory-quarantine.ts` + 3 hook factories + wiring in `index.ts`. A per-`runQuery` `processedExternalContent` flag flips when (a) the prompt body carries a `<untrusted-input source="...">` wrap (UserPromptSubmit), or (b) any PostToolUse hook emits a #321 marker — the flag-flip reuses #321's existing classifiers (`inferReadSource` for MCP read tools, `inferSentinelSource` for built-ins) so a future emitter prefix flips the flag automatically. PreToolUse on `Write` / `Edit` checks the flag when the target resolves under `/workspace/trusted/` (excluding the carved-out `quarantine/` subtree). When set, `Write` is intercepted: the hook itself persists the model's content to `/workspace/trusted/quarantine/<session-id>/<rel-path>` (sessionId sanitized — alphanumerics + hyphen + underscore only; path-traversal chars collapse to `_`) and denies the original call — the redirect is structural, not dependent on agent cooperation. `Edit` denies hard with a redirect-explainer reason, since surgical-edit semantics don't survive a redirect to a fresh quarantine snapshot. Redirect uses atomic write (temp + rename) so a concurrent promote operation can't observe partial JSON. Failure to write the quarantine target fails closed — original `/workspace/trusted/` write is denied to keep the trust boundary intact, and the operator is asked to fix subtree permissions. Path resolution mirrors #321's traversal-defeated normalization so `/workspace/trusted/../../etc/x` doesn't accidentally trip the gate (path falls outside the prefix; #322 handles it). Out of scope for v1: host-side notification when a quarantine record lands; `nightly-housekeeping` exclusion from weekly summaries; compaction-summary exclusion (rolls under #327). Closes the laundering channel called out in #325's body — webpage → daily log → weekly summary → indistinguishable from operator-typed fact.

- Rate limits on `Task` (sub-agent spawn) and `mcp__nanoclaw__schedule_task` (#323). New PreToolUse hook in the agent-runner — `rate-limits.ts` + wiring in `index.ts` — applies provenance-conditional per-hour caps. Walk-back reuses #322's `walkBackIterableForProvenance`, classifying the call into one of five rows: operator-trusted (50 spawns/hr, 30 schedule_task/hr — audit-log only, never denies), operator-untrusted (5/3), untrusted-source (web/email/scraped → 2/1), cross-group from non-owner (2/1), or mixed chain (any untrusted link → 2/1). The `__unknown__` sentinel from #322's classifier collapses to `untrusted-source` so a future emitter prefix can't silently bypass the gate. Counter file at `/workspace/state/rate-limit-counters.json` is group-scoped — an injection in one chat can't poison another chat's counters; rolling-window pruning bounds file size by the highest cap (operator-trusted: 50 spawns/hr). Atomic write (temp-file + `renameSync`) keeps concurrent readers from observing partial JSON. Loader fails open on validation errors (denying every spawn from a corrupt file is worse than losing the counter; per-hour cap means the new window starts immediately). Optional operator-tightening file at `/workspace/trusted/rate-limit-overrides.json` lets the operator lower any row's caps or flip the trusted-operator row from audit-only to enforced; non-trusted rows can't be flipped TO audit-only via override (would defeat the gate), and negative cap values clamp to the default rather than silently disabling. Override file is host-only-writable, mirroring #320 / #324. Out of scope for v1: recursion-depth tracking on Agent spawn (needs SDK-level depth propagation), global ceilings across groups (host-side coordination), per-chat active-task and cron-recurring caps (per-hour rate caps already gate the fork-bomb case).

- Composio outbound argument validator (#326). New PreToolUse hook in the agent-runner — `composio-arg-validator.ts` + wiring in `index.ts` — gates `mcp__composio__gmail_(send|reply)*` and `mcp__composio__slack_(post|send)*` on per-field shape constraints before bytes leave the container. Header fields (`subject`, `to`, `cc`, `bcc`, `recipient_email` for gmail; `channel`, `user` for slack) reject `\r`/`\n` and cap at the RFC 5322 998-byte line limit so a model can't synthesize header injection (`subject = "Hi\n\nBcc: attacker@evil.com"`). Body fields (`body` for gmail, `text` for slack) cap at 100 KB measured as UTF-8 bytes (not chars — multi-byte content can't slip past a chars-based limit) and reject ASCII control chars except `\t` and `\n`; `\r` is in the reject set because CRLF in a body is the common header-spoof pattern. Array variants of `to`/`cc`/`bcc` are validated element-by-element so an injection can't ride in via the array shape when the scalar shape is gated. Wrong-type values (number where string expected) deny with `wrong_type`. Tool-only — does not look at provenance, since header injection and oversize bodies are wrong regardless of who issued the call (operator pays the same gate; the operator can never legitimately produce a `\n` in `subject`). Runs BEFORE #320's egress allowlist so a malformed arg is rejected without paying the transcript-walk cost. Logged-deny field is the field name only, never the value, per `no-secrets` (body / recipient strings carry tokens or PII). Composio read tools, github mutations, and calendar mutations pass through unchanged — adding a row to `TOOL_RULES` is a one-line change when a new outbound surface appears. Symmetric counterpart to #117's incoming-result sanitizer.

Tessl mutating verbs (`install`, `login`, `update`, `uninstall`, `new_tile`) and the local-only `status` stay un-wrapped by omission. Closes the third-party-MCP and built-in-search gaps called out in #321's body.

- Destructive-op confirmation tokens (#324). The `## Facts` checkpoint writer fires at threshold-cross (always-on, validates the file format on real transcripts before the destructive flip relies on it), rotating `default.md → previous.md` first then writing the orchestrator-deterministic Facts section to `<group>/.checkpoints/default.md` — mutating-tool taxonomy filter (Write, Edit, MultiEdit, NotebookEdit, Skill, every `mcp__nanoclaw__*` mutator, Task, TeamCreate/Delete) plus a Bash read-only argv allowlist (cat, ls, grep, find, head, tail, wc, sort, uniq, pwd, echo, file, stat, date, plus `git status/log/diff/show/rev-parse`) keeps the "do NOT re-execute" list focused on real state changes. The agent-runner's existing SessionStart auto-context hook now ALSO loads `/workspace/group/.checkpoints/default.md` as a CHECKPOINT section (last, closest to the prompt for max salience) so the next session after a nuke picks up the prior facts deterministically. A user-invocable `/session-reentry` skill ships as the manual fallback. **Behaviorally inert by default** — `ENABLE_THRESHOLD_NUKE=0` keeps SDK auto-compaction on and the orchestrator's `nuke_session` call gated off; the orchestrator only logs `threshold_nuke_inert (ENABLE_THRESHOLD_NUKE=0)` at warn-level when the threshold crosses. When the operator flips `ENABLE_THRESHOLD_NUKE=1`, `DISABLE_COMPACT=1` is set on every container spawn AND the threshold-cross handler calls `nuke_session` for the default slot after the current turn completes — the next inbound spawns a fresh container which auto-loads the checkpoint via the SessionStart hook. The flag-off period is the data-collection window: ssh nas + grep `'session_tokens|threshold_nuke'` on host-logs to curve real-session usage distributions before flipping.
- `wipeSessionJsonl` now also removes the sibling per-session tool-results directory at `<slug>/<sessionId>/` alongside the JSONL transcript (#202, follow-up to #193). The SDK writes tool-call result snapshots (image attachments, search outputs) into that directory; pre-fix it was orphaned by every scheduled-task run and by every `nukeSession` call (since the helper is shared). Implemented via a new `removeToolResultsDirInSlug` helper that mirrors `unlinkJsonlInSlug`'s lstat → branch on type → realpath-containment discipline: a symlink at the dir path is unlinked as a link (target preserved), a regular file is left alone (logs warn — not the SDK's shape), and a real directory is removed via `fs.rmSync({ recursive: true })` with `ENOENT` handled explicitly in the catch so the returned delete count stays accurate (a concurrent cleanup that vanishes the path between lstat and rm returns 0, not 1). Node's `rmSync` does not follow symlinks during recursion, so a compromised container that scattered host-pointing symlinks inside its own tool-results dir cannot redirect the wipe outward. The `wipeSessionJsonl` return count is now up to 2 per slug (1 transcript + 1 tool-results dir) rather than 0–1.
- Added `unregister_group` MCP tool — main-group only inverse of `register_group` (#159). Removes the `registered_groups` row, cascade-deletes scheduled_tasks tied to the unregistered folder, and refreshes `available_groups.json` in one call; refuses to touch the main-group registration; leaves the on-disk `groups/<folder>/` directory intact (operators delete that manually). Companion one-shot cleanup at `initDatabase()` drops the dormant `tg:1698969` / `telegram_main` row that lingered because there was no inverse path until now. Companion drift detector logs (does not auto-delete) any `registered_groups` row whose JID has no matching `chats` row at startup, so future drift surfaces immediately.
