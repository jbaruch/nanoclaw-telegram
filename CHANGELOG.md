- Three new IPC handlers close the missing UX surface for #415's trigger-pattern learner — `promote_learned_trigger`, `reenable_learned_trigger`, `delete_learned_trigger`, and the read-side `list_learned_triggers` (covers #451 items 1, 2, 3; item 4 — producer-side enrichment of `haiku classifier verdict` with `messageId` + `inboundText` — touches `src/gates/haiku-classifier.ts` plus the host-log-parser contract and is its own scope per the issue body, deferred to a follow-up). The trigger-pattern learner (`src/gates/trigger-learner.ts`) writes proposals as `source: 'learned'` + `enabled: false`; the trigger gate (`src/gates/trigger.ts`) skips `enabled: false` rows so proposals are inert until promoted. Authorization mirrors `set_agent_model` (#395) — owner-of-bill semantics: main can target any group, non-main can target only its own folder. List honours the same scope: non-main with no `groupFolder` filter is implicitly scoped to the source folder, and an explicit cross-folder request is denied with a typed error. - Composio's REST and MCP gateways maintain independent key namespaces — verified empirically 2026-05-06 against `backend.composio.dev` (REST, header `x-api-key`, accepts project-scoped `ak_*` keys) and `connect.composio.dev/mcp` (MCP, header `x-consumer-api-key`, accepts consumer-scoped `ck_*` keys). The legacy single-`COMPOSIO_API_KEY` shape (introduced in #107) used the same env var for both surfaces; once Composio's REST gateway started rejecting `ck_*` keys with `Invalid API key` 401s, the inline-fetch path in `tessl__composio-fetch`'s precheck broke while MCP-mediated tools kept working — exactly the operator surface a single env var can't represent. Splits the wiring so each surface gets its own correctly-scoped secret: `COMPOSIO_API_KEY` stays on the REST surface (now expected to hold the `ak_*` project key the backend wants for `x-api-key`), and a new `COMPOSIO_MCP_KEY` carries the consumer-scoped `ck_*` key the agent runner sends as `x-consumer-api-key` to the MCP gateway. Both forwarded into agent containers via `CONTAINER_VARS` in `src/container-runner.ts` (gated to main + trusted tiers, untrusted groups still receive nothing) and routed through the secret env-file (mode 0600) per `SECRET_CONTAINER_VARS` so neither value ever appears on the docker process command line. Agent runner's MCP server registration in `container/agent-runner/src/index.ts` now reads `COMPOSIO_MCP_KEY` instead of `COMPOSIO_API_KEY` for the `x-consumer-api-key` header. Lockstep `.env` migration required: copy the existing `COMPOSIO_API_KEY` value (a `ck_*` consumer key in current deployments) into a new `COMPOSIO_MCP_KEY` line, then either replace `COMPOSIO_API_KEY` with the new `ak_*` project key from the Composio dashboard (recommended — restores REST) or leave it on `ck_*` until the project key is provisioned (REST stays 401 but MCP keeps working). `.env.example` documents the surface split, header conventions, and prefix expectations so the operator-side contract is auditable. Tests in `src/secret-env-file.test.ts` lock down both keys in `SECRET_CONTAINER_VARS` and the env-file emitting both values together. No fallback shim — the environment variables decide which surfaces work; missing either disables that surface explicitly.
- `mcp__nanoclaw__list_tasks` no longer throws `t.prompt.slice is not a function` when any row in `scheduled_tasks` has a BLOB-typed `prompt` column (#512). Reader-side: the per-row formatter inside `container/agent-runner/src/ipc-mcp-stdio.ts` is extracted into a pure `formatTaskRow(t)` helper in `format-task-row.ts` that coerces the prompt regardless of shape — `string` passes through, `null`/`undefined` becomes empty, `{type:'Buffer',data:[...]}` (the post-`JSON.stringify(Buffer)` shape better-sqlite3 produces for BLOB columns) decodes via `Buffer.from(...).toString('utf8')`, and any other shape falls through to `String(...)` so the line still appears rather than poisoning the entire listing through the outer try/catch. Writer-side: a new `src/coerce-task-prompt.ts` helper (`coerceTaskTextField`) is wired into `src/ipc.ts`'s `schedule_task` and `update_task` handlers — string passthrough, JSON-Buffer shape decoded to UTF-8, every other shape rejected with a WARN log so the IPC drops rather than persisting `"[object Object]"` for a malformed payload (a row that would later fire with garbage as its prompt). The persisted contract is now "prompt is always real TEXT in the DB", with the reader's coercion as defense-in-depth for any historical BLOB row already on disk. Adds `format-task-row.test.ts` (12 cases pinning the reader's shape coercion + truncation + missing-field tolerance), `coerce-task-prompt.test.ts` (11 cases pinning the writer's decode + reject contract including multi-byte UTF-8 round-trip), and four new cases in `ipc-auth.test.ts` covering schedule_task / update_task decode-and-reject end-to-end. New `containerConfig.maintenanceAgentModel` field on `RegisteredGroup`. Resolution ladder for maintenance spawns (`sessionName === MAINTENANCE_SESSION_NAME`): `maintenanceAgentModel` → `agentModel` → global `AGENT_MODEL` → `DEFAULT_AGENT_MODEL`. Non-maintenance spawns are byte-identical to the pre-#509 ladder — the user-facing chat never accidentally routes through the maintenance override even when both fields are set on the same group. Same validation as the existing per-group override (`resolvePerGroupAgentModel` against the user-facing-resolved value as the maintenance fallback — so a fat-fingered maintenance value falls back to the user-facing per-group choice rather than silently jumping to the global default and bypassing the operator's intentional per-group routing). DEFAULT_SESSION_NAME` resolution at the existing call site); the per-spawn info log gains a `sessionName` field. - Session-length cap prevents `cache_read` explosion on long-lived sessions (#413). Without an upper bound on a Claude Code session's lifetime, a single session keeps re-reading the entire prior context as `cache_read` on every turn — observed at >18M `cache_read` in a single query on the 2026-04-26 `telegram_main` SmartThings history-build run (498 internal SDK turns over 75 minutes; one query consumed `cache_create=4,819,008 + cache_read=18,210,198` ≈ 700+ fresh-session-equivalents). The SDK's auto-compact summarises but does not delete; summary plus subsequent turns keep growing on top. The new cap tracks **cumulative** per-session totals (sum of `usage.input_tokens` across all turns + turn count) and forces a fresh-session boundary when either threshold trips. Distinct from the existing per-turn `ENABLE_THRESHOLD_NUKE` path, which fires only when a single turn's `input_tokens` crosses a percentage of the context window — a session can stay below that per-turn threshold for hours while still accumulating past the cumulative cap. Configured via two env vars in `src/config.ts`: `SESSION_TOKEN_CAP` (default 1,000,000) and `SESSION_TURN_CAP` (default 100); a non-positive value disables that specific threshold without disabling the other. Both validated at startup with the same `parseInt` / positive-integer check pattern as `AGENT_AUTO_COMPACT_WINDOW`. Threshold detection fires AFTER each assistant turn completes — the `wrappedOnOutput` callback in `runAgent` (`src/index.ts`) calls the new `recordSessionTurn` DB helper to upsert running totals, then `shouldMarkForReset` (pure logic in `src/session-length-cap.ts`) classifies the post-turn snapshot. When the verdict says reset, `markSessionForReset` flips `marked_for_reset = 1` on the row and persists the trip reason (`'token_cap'` vs `'turn_cap'`) plus the cap value at trip time so the user-facing notification reflects what was actually configured when the threshold tripped, not whatever the env says when the next inbound spawn consumes the marker. Reset itself happens on the NEXT inbound message (never mid-turn): `consumeSessionReset` reads-and-deletes the marked row in a single transaction, the orchestrator builds a brief context-handoff prefix from the most recent assistant turn (`getLastFromMeMessage` → `buildHandoffPrefix`, capped at 400 chars with whitespace collapsed) and prepends it to the prompt the new container sees, drops the stale `sessionId` from BOTH the in-memory cache and the `sessions` DB row so the SDK spawns fresh, and fires the in-band notification (`buildResetNotification`) via the channel router before the spawn — the user sees "Session reset: cumulative input tokens crossed 1,000,000 — starting fresh to keep context bounded." before the agent's first reply arrives. New SQLite table `session_length_state` (state migration `state-011-session-length-cap`, owner skill = orchestrator, schema doc at `src/session-length-cap.schema.md`) carries `(group_folder, session_name)` PK matching the existing `sessions` table key shape, plus `total_input_tokens`, `turn_count`, `last_handoff_summary`, `marked_for_reset`, `reset_reason`, `reset_cap`, `started_at`, `last_updated_at`, and `schema_version` — `schema_version` from day one per `rules/stateful-artifacts.md`. The writer (`recordSessionTurn`) detects rare drift (row exists but `session_id` differs from the live SDK chain — happens when the SDK rotated under us without going through the cap-state reset path) and treats it as a fresh row via `INSERT OR REPLACE` so accounting always lines up with the active `session_id`. `markSessionForReset` is idempotent (the WHERE clause excludes already-marked rows so a second call from a multi-message single runQuery doesn't churn the `last_updated_at` or overwrite the reason that actually fired first). `consumeSessionReset` is atomic (read-then-delete in one transaction) so the second inbound after a reset returns null rather than double-resetting. Group nuke (`/nuke` IPC handler) now also calls `clearSessionLengthStateForGroup` so a forced reset wipes cap accounting alongside the SDK session — without it a stale `marked_for_reset = 1` row could survive against a `session_id` that's already gone, producing a noisy log line on the next spawn. Three new test files cover the seam: `src/session-length-cap.test.ts` (15 cases — boundary correctness for both caps, deterministic precedence when both fire simultaneously, disabled-cap handling, handoff-prefix builder including the 400-char truncation and whitespace collapse, notification formatting), `src/session-length-db.test.ts` (16 cases over fresh in-memory SQLite via `_initTestDatabase` — UPSERT semantics, `last_handoff_summary` write-once via COALESCE, slot independence, idempotent mark, atomic consume, full lifecycle accumulate-→-mark-→-consume-→-fresh-INSERT under a new `session_id`), and `src/state-migrations/state-011-session-length-cap.test.ts` (5 cases — bumps `user_version` to 11, no collision with the existing `sessions` table, `schema_version` shape, composite PK, nullable `reset_reason` + `reset_cap`).
