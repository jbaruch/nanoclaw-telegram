# Agent source cache owner

`src/agent-source-cache.ts` solely writes and reads the host-only `data/sessions/<registered-group>/agent-runner-source.json` admission marker. `src/container-runner.ts::buildVolumeMounts` invokes this owner before mounting that group's writable `agent-runner-src` at `/app/src`. The marker is a sibling outside this agent bind; it contains no credential or user prompt. These components ship together.

Schema 1 has exactly `schema_version:1`, `state` (`refreshing` or `ready`), and `source_sha256` (64 lowercase hex characters). This is a gate-store exception: malformed, linked, foreign-owned, unsupported/unknown-version or ambiguous marker state refuses launch with an actionable diagnostic, never reads as no gate. No earlier marker versions are accepted or migrated. A genuinely absent marker, including an existing legacy cache with only mtime freshness, requires canonical refresh before a ready record is established; it never adopts recalled mtimes.

Every canonical regular file's name, byte length and exact bytes contribute to the SHA256. The current shipped source layout is flat, with required `index.ts` and `ipc-mcp-stdio.ts`; new directories, aliases or other types HOLD rather than being skipped. Bounds are 128 files and 4 MiB total source bytes; the marker is bounded to 512 bytes. Canonical sources are read nofollow/single-link and re-fingerprinted before ready publication. Names or contents are not logged. The fingerprint records the canonical base delivered, not current customized cache bytes or execution/delivery authority.

Same canonical digest plus a ready marker and present entrypoint directory entry preserves customized shipped bytes. Presence uses nofollow metadata: a custom link resolves in the container namespace, and its host target is neither followed nor used to decide refresh. A canonical change, missing cache/entrypoint, absent marker or known refreshing state refreshes shipped names from current canonical bytes. This preserves existing merge semantics: shipped names may be overwritten on canonical refresh, while custom-only extras stay untouched. No recursive deletion of the customized cache occurs. An existing customized directory that conflicts with a shipped filename refuses before refresh. Cache leaf symlinks/hardlinks are replaced atomically, never written through; their foreign targets remain untouched.

The owner verifies native same-writer parent/cache directory identities using nofollow held descriptors and binding checks. Existing runtime-owned structural roots only lose group/other write bits; newly created empty cache roots have explicit 0755 mode. Canonical code files use explicit 0644 and the private marker 0600. Staging is private and outside the writable bind. Linux publication uses held directory capabilities; portable publication uses the protected parent and repeated native binding checks. No agent-supplied path, role, environment flag or reset is accepted.

A fsynced atomic `refreshing` marker and parent barrier precede the first cache replacement. Source leaf candidates are flushed and atomically renamed, the cache is flushed, copied bytes are verified and the canonical fingerprint is checked again. Only then can a flushed atomic `ready` record be published and its parent flushed. Native failure propagates; partial copies remain refreshing and cannot silently become usable merely because canonical source later rolls back. The owner can reconstruct that known refreshing state from the current canonical source on the next invocation. Unknown markers remain unchanged; there is no force/reset or credential/effect retry route. Cleanup failures propagate with the primary error. This is a synchronous host owner, not a cross-process locking claim.
