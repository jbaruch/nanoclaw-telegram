# Durable agent request contract

The agent `container/agent-runner/src/ipc-mcp-stdio.ts::writeIpcFile` writes schema-1 message/task JSON. Host `src/ipc.ts::validateIpcRequest` reads it at ingress. Host-private custody schema (`.claimed-v1/owner.json`) versions custody only; each payload independently contains `schema_version: 1`. These components are co-shipped.

Each payload is an object with version 1 and a supported `type`. `message` requires string `chatJid,text`; `react_to_message` requires `chatJid,emoji`. Task requests are `schedule_task` (prompt,schedule_type,schedule_value,targetJid), `pause_task`, `resume_task`, `cancel_task` (taskId), `update_task` (taskId and a changed prompt/script/schedule field), `refresh_groups`, and `register_group` (jid,name,folder,trigger). Required strings are nonempty. The reader validates optional string routing/metadata, nullable script, schedule/context enums, requiresTrigger boolean and containerConfig/mount field types before effects. Timestamp, createdBy/groupFolder, isMain and sender are advisory context, never host authorization or delivery evidence.

Legacy unversioned and unknown/future versions refuse before dispatch. Exact raw bytes remain in host quarantine and are never silently upgraded, replayed or treated as delivered. Unknown in-flight custody stays held across restart. Repair the co-shipped writer/reader and reconcile native effects before owner-approved replay; there is no automatic migration or force control. A supported request still needs actual registered-source and live DB/channel checks. Agent role flags grant no authority. Tool text confirms queueing only; native channel receipts establish delivery.

The message/task discriminator fixes the channel. Existing request byte/custody bounds, immutable snapshots and nofollow/single-link checks remain. Atomic publication flushes the file and both participating directories before acknowledging queueing; uncertain publication failures never retry an effect.

The task-create boundary converts only native primary-key ID conflicts from its single atomic INSERT into input refusal. It never replaces the existing row or chooses a fresh ID for a retry. The conflicting request stays in quarantine, later valid requests can proceed, and unrelated native SQLite/schema/implementation failures still reach the host lifecycle owner.


Host follow-up input is a separate schema-1 contract: `src/group-queue.ts::sendMessage` writes an atomic JSON file under the registered group's `input/`; `container/agent-runner/src/index.ts::drainIpcInput` reads it. Exact fields are `schema_version:1`, `type:"message"`, and nonempty string `text`. This is host-to-agent input, not a channel-delivery receipt. Unsupported, legacy or malformed-shape input stays byte-preserved and is not admitted to the SDK; later compatible input can progress. No automatic migration exists: reconcile retained input with the co-shipped writer/reader before explicit owner repair. Known malformed JSON remains refused by the existing cleanup path; native read failures retain pending files and already-collected valid input. `_close` is the fixed empty control sentinel, not a JSON payload or proof of completed work.


Every observed channel entry moves individually through the existing native request-slot custody. Only `.json` leaves can become dispatch claims; non-request filenames enter the same durable per-leaf rejection quarantine described below, without reading their contents. The owner never moves the whole captured inbox to quarantine. A `.json` published through an already-held old directory after enumeration remains in that inbox for the next scan; final removal succeeds only for an actually empty directory. Thus late queued input is not swept into non-request evidence. Native rename/fsync uncertainty and unknown in-flight holds remain unchanged.

Existing `errors/unrecognized-<native-batch-id>/inbox` whole-inbox evidence is verification-only. Its `owner.json` schema-1 fields remain exactly `schema_version`, `source_group`, `channel`, `batch_id`; source identity must match, and only an already-retained directory with no original inbox can pass renewed durability checks. An incomplete move, ambiguous source, unsupported or changed metadata remains held unchanged for owner reconciliation. There is no new whole-inbox move, migration, automatic replay or eviction.

Required MCP fields use matching nonempty string constraints before publication (message text, reaction emoji, scheduled prompt/value, task IDs and group registration fields). Optional update fields retain their existing semantics, including empty script removal; live host authorization and database checks still apply. GroupQueue refuses empty follow-up text before writing a record. The scheduled-script tool describes optional object activation data (omission defaults to `{}`); no script result or queued record proves delivery or supplies new send authority.


Known invalid captured JSON leaves and non-request filenames share a pre-dispatch disposition: `errors/rejected-<native-batch-id>-<native-request-id>/captured` retains the entry itself, including symlink, hardlink, FIFO or directory. `src/ipc-inbox.ts` solely writes/reads sibling `owner.json`, with exact schema-1 fields `schema_version`, `source_group`, `channel`, `batch_id`, `request_id`, `file`, `reason` (`invalid_or_unreadable_input`). No target or unknown child is followed, parsed or deleted by quarantine. A non-request filename, bounded-regular/link/type/size refusal, or native ELOOP/EACCES/EPERM while opening/reading captured input takes this path; native storage I/O, snapshot-write, rename or fsync uncertainty stays held. The exact existing quarantine is revalidated and flushed on restart before empty request-slot retirement. A pending snapshot or in-flight intent alongside rejection is ambiguous and holds; no effect is inferred safe, replayed or acknowledged. Valid other requests can progress, and refused input never consumes permanent live-claim capacity after verified custody transfer. Unsupported/changed metadata remains unchanged for owner repair; there is no automatic migration or eviction.


An `update_task` producer call must include at least one prompt, script or schedule field before it can publish schema 1; the host retains the same requirement. Omission is distinct from an explicit empty script, which remains a supported script-removal update. Neither queued update nor source validation proves a native effect or delivery.


The non-authoritative channel work hint treats any observed entry as work, including a lone non-JSON file, directory, alias or FIFO. It reads only directory-entry metadata, closes its handles and still requires native identity checks plus private per-entry custody before any parse/effect. Empty channels remain an idle no-write path. Co-shipped agent source refresh is owned by `src/agent-source-cache.ts` and documented in `docs/AGENT-SOURCE-CACHE.md`; mtimes cannot authorize an old protocol producer.


Live custody admission retains the global 1024-batch bound and additionally limits a validated native source group to 64 live batches, across messages and tasks. The sole inbox owner counts the same private schema-1 batch identities used by the dispatch reader, before any new capture mutation. At the source limit, that channel stays in place for owner reconciliation; other sources can still use the remaining global capacity. Unknown/unsupported/unreadable private owner metadata remains held and consumes global capacity, never supplies a guessed positive source identity and is never evicted or reset. Already-existing excess source batches are preserved; the cap prevents new capture until real retirement frees capacity. Request filename ordering, over-budget inbox holds, pending/in-flight outcomes and payload admission remain unchanged. Native record reads allocate from observed filesize and can grow only to the existing 1 MiB bound; the new bounded metadata scan does not allocate a full payload for each small owner record. No caller quota flag or reset is exposed.
